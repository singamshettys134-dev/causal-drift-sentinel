# Causal Drift Sentinel
### A Production ML Agent for The DataHub Agent Hackathon — Production ML Agents Track

---

## 1. Problem Statement

ML models fail silently in production. A model's accuracy can degrade for weeks before anyone notices — by the time a dashboard shows "accuracy dropped 8%," the business impact is already done. The real question no one can answer fast enough is: **"Which upstream data change actually caused this, out of the dozens of tables and pipelines feeding this model?"**

Today, answering that question means a data scientist manually tracing lineage across wikis, Slack threads, and tribal knowledge — often taking days. Meanwhile:

- **Feature drift** goes undetected because no one is comparing today's feature distributions to training-time distributions.
- **Silent schema-compatible breakage** happens when a column keeps its name and type but its *meaning* changes (e.g., a currency field switches from USD to local currency, a categorical encoding shifts) — nothing crashes, but predictions quietly get worse.
- **Root cause is guessed, not proven.** Engineers see correlation ("this table changed around the same time") and assume causation, often fixing the wrong thing.

DataHub already holds the answer to "what feeds what" via its ML lineage graph (training data → features → models → deployments). No one is using that graph to *automatically diagnose* production ML failures. That's the gap this project fills.

---

## 2. What We're Building

**Causal Drift Sentinel** is an autonomous agent that:

1. **Watches** a model's live prediction distribution and output quality over time.
2. **Detects** when something is statistically wrong — not just "accuracy dropped" but precisely *which* feature(s) drifted and by how much.
3. **Traces backward** through DataHub's ML lineage graph to isolate the *specific upstream dataset or pipeline change* that caused the drift — distinguishing genuine causes from tables that merely changed around the same time.
4. **Explains** the finding in plain language, generated by a large, powerful LLM reasoning over the statistical evidence and the lineage graph together.
5. **Writes back** the diagnosis as a structured incident directly into DataHub, and opens a GitHub issue/PR with a concrete suggested fix (e.g., "retrain on refreshed feature X" or "add a validation gate on table Y") — so the next engineer, or the next agent, inherits the finding instead of starting from zero.

This is not a wrapper that asks an LLM "why did my model break?" and hopes for a good guess. The LLM's job is reasoning and explanation *on top of* real statistical evidence and a real graph traversal — the causal isolation itself is done algorithmically, and the LLM is the layer that makes the result legible, actionable, and written back in polished form.

---

## 3. Why This Is Technically Sophisticated (Not a Thin LLM Wrapper)

| Layer | What it does | Why it's hard |
|---|---|---|
| **Lineage graph ingestion** | Pulls full ML lineage from DataHub via the MCP Server / Agent Context Kit and materializes it as a traversable DAG (training data → features → model → deployment) | Requires correctly modeling multi-hop lineage, not just direct parent-child edges |
| **Statistical drift detection** | KS-test and Population Stability Index (PSI) for numeric/categorical feature drift; embedding centroid distance (cosine shift) for unstructured/text features; distributional drift on the model's own prediction outputs over time | Real applied statistics, not "ask the LLM if this looks different" |
| **Causal root-cause isolation** | When downstream drift is detected, the agent walks the lineage DAG backward and tests each upstream node independently for drift, using a simplified intervention-style check (e.g., holding other upstream nodes constant) to separate genuine causes from coincidental correlation | This is the novel core of the project — most teams stop at "something changed nearby" |
| **LLM reasoning & explanation layer** | A frontier-class LLM takes the statistical evidence + graph trace and produces a structured, human-readable root-cause report and a concrete suggested fix | High-quality reasoning over structured evidence, not free-form guessing |
| **Autonomous write-back** | Agent writes the incident back into DataHub as a structured annotation and opens a GitHub issue/PR with the diagnosis | Closes the loop — the next person or agent inherits the knowledge automatically |

### Backend
- **Framework:** FastAPI (Python) — matches ecosystem needs for statistical libraries.
- **LLM backend:** Use the most capable available frontier model for the reasoning/explanation layer (e.g., Claude Opus-tier or equivalent top-of-line model) via API — this is the layer judges will see "think," so model quality matters most here. Keep this swappable via a single config value so the model can be upgraded without touching the pipeline.
- **Stats:** `scipy` (KS-test), custom PSI implementation, `sentence-transformers` or similar for embedding centroid drift on text features.
- **Graph:** `networkx` to represent and traverse the DataHub lineage DAG.
- **DataHub integration:** DataHub MCP Server (or Agent Context Kit) for reading lineage/schema/ML metadata, and for writing back incident annotations.
- **GitHub integration:** GitHub API (or MCP GitHub server) to open the diagnosis issue/PR automatically.

### Frontend
- **Framework:** React (Vite).
- **Views:**
  1. Live lineage graph (visualize the DAG DataHub returns, highlight the drifted node in red).
  2. Drift timeline (statistical charts — distribution shift over time).
  3. Root-cause report (LLM-generated explanation, formatted clearly).
  4. "Replay a failure" demo mode — lets judges trigger a synthetic drift scenario live and watch the whole pipeline run end-to-end. **This view is critical for the demo video and for judges testing it live.**

### Data for the Demo
Use a synthetic but realistic dataset (e.g., an e-commerce or fraud-detection style pipeline) registered in a demo DataHub instance, with:
- A training dataset → engineered features → a deployed model, all linked via lineage.
- A scripted "injection" of drift into one specific upstream table, so the demo can reliably reproduce the agent catching it and tracing it back correctly.

## 6. Build Order (No deadline pressure — build this properly, in this order)

1. Stand up a demo DataHub instance with a realistic lineage graph (training data → features → model → deployment).
2. Build the lineage ingestion layer — pull the graph via MCP Server, represent it as a DAG.
3. Build the statistical drift detection engine and validate it against synthetic drift you inject yourself.
4. Build the causal root-cause isolation logic — this is the hardest and most important part; get this right before touching the LLM layer.
5. Wire in the LLM reasoning layer — feed it structured evidence (drift stats + graph trace), not raw data, so its explanations stay grounded and don't hallucinate.
6. Build the write-back agent (DataHub incident + GitHub issue/PR).
7. Build the React frontend, ending with the "Replay a failure" demo mode.
8. Polish, write the `examples/` folder, write the README, add the LICENSE.
9. Record the demo video last, once the full pipeline runs reliably end-to-end.

## 7. Instructions for Whoever (or Whatever) Builds This

If you are an AI coding assistant reading this document: build to this specification exactly. Prioritize getting the **causal root-cause isolation logic** (Section 3, Section 6 step 4) correct and defensible — that is the technical core the entire project's credibility rests on. The LLM reasoning layer should never be asked to invent a root cause; it should only be asked to explain and phrase a root cause that the statistical/graph engine has already isolated. Keep the LLM model choice configurable in one place so it can be swapped for the most capable available model without refactoring.
