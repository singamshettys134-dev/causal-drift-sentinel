# Examples

Sample outputs so judges can evaluate quality without running the code
(spec Section 5: "Sample outputs").

All four files below are derived from a single real run of the pipeline
against the scripted demo scenario in `backend/app/utils/demo_data.py`
(silent cohort shift in `raw_user_profiles.account_age_days`, per spec
Section 4's "Data for the Demo"):

| File | What it is | How it was produced |
|---|---|---|
| [`sample_root_cause_trace.json`](./sample_root_cause_trace.json) | The raw structured evidence: prediction drift, every upstream candidate tested, and the isolated root cause(s) | Actually computed by `drift/engine.py` + `causal/isolator.py` against the synthetic demo data — this is real statistics, not fabricated numbers. |
| [`sample_root_cause_report.json`](./sample_root_cause_report.json) | The LLM reasoning layer's output: plain-language diagnosis + suggested fixes | Composed following `llm/reasoning.py`'s strict system prompt contract (only phrase causes already present in `isolated_root_causes`, ground every number in the trace). This sandbox has no live `GROQ_API_KEY` configured, so this one file's prose was written by hand under that same contract rather than via a live API call — everything else here (the trace, the issue body, the incident payload) is generated directly by running the actual code. |
| [`sample_github_issue.md`](./sample_github_issue.md) | The GitHub issue the write-back agent opens | Generated by directly calling `writeback/agent.py::_render_github_issue_body()` on the report above — byte-for-byte what a live run produces. |
| [`sample_datahub_incident_payload.json`](./sample_datahub_incident_payload.json) | The structured incident annotation written back to DataHub | Generated by directly calling `writeback/agent.py::_render_incident_payload()` on the report above. |

## What this demonstrates

Notice in `sample_root_cause_trace.json` that **two** nodes show identical
raw drift statistics (`raw_user_profiles` and `feature_user_risk_score`,
both KS=0.8948) — because the second is a near-deterministic transform of
the first. A naive "closest drifted node" or "most correlated node"
approach would have trouble ranking these, or might over-credit whichever
node happens to sit closer to the model. The `intervention_delta` field is
what separates them: `raw_user_profiles` collapses ~78% of the downstream
drift when held at baseline (`0.7767`), while `feature_user_risk_score`
collapses almost none of it (`0.0005`) once the true upstream cause is
accounted for — so it's correctly flagged `is_genuine_cause: false` and
`confounded_with` lists the nodes it was entangled with. That distinction
is the project's technical core (spec Section 3 & 7).

## Reproduce this yourself

```bash
cd backend
pip install -r requirements.txt --break-system-packages
export USE_MOCK_DATAHUB=true
export GROQ_API_KEY=gsk_...   # for the live LLM report + write-back
uvicorn app.main:app --reload
# then: curl -X POST "http://localhost:8000/api/investigate?inject_drift=true"
```
